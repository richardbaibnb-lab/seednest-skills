# OPERATION-QUICKBOOK每月银行收入对账

## 要完成的事

首先回答：**目标月有哪些客人最终仍未付清、应催收多少；以QuickBooks连接银行的实际收款为主要依据。** 同时回答平台已代收的钱是否进入正确银行账户。客人欠款与平台打款未核实分开，不能因目的银行缺流水而把已付客人列为欠款。

用户2026-10-11明确：Vrbo全部经Stripe收款。本用户的Vrbo/Stayz/HomeAway按Guesty订单→Stripe实际支付→打款批次→QuickBooks银行核查；无需为完成收款核查而坚持登录受限的Vrbo网站。保留网站登录状态与处理商覆盖状态，遇到未同步订单、分期或退款争议再补相应渠道证据，不声称已登录Vrbo。

用户每月7号左右会另跑月度技能，将收入支出记入飞书。本技能独立复核资金链，不重复录账。既从平台往银行查漏款，也从银行反查收入来源；不能只核对月合计或只看 QuickBooks Pending。

- “创建技能并查一查”时，也应按飞书清单逐一登录全部相关账户，实查身份、收入类型、收款路径和样本；用户已于2026-10-10强调“账户都要登录”。不能以一个平台一个样本替代其他账户，也不能只更新规则而不完成可做的登录检查。确有人工验证或网站限制时记录具体账户、阻碍和可续做入口，继续其他独立部分；不得把探查样本说成整月对账完成。
- “运行本月/某月对账”时，执行下述完整流程，交付可追溯明细和未结差异；某平台暂不可访问时先完成独立部分。
- 当前请求授权查询、沿用正常登录、下载报表及生成本地报告。本技能本身不授权付款、扣客人款、退款、提现、修改银行收款信息、确认平台收款、发消息、修改飞书账目或在 QuickBooks 执行 Post、Match、Undo、Reconcile、规则修改。发现需改账的项目列出依据供后续处理。

结论单列“用户规则通过（平台/Stripe已转款；银行未验证）”，不再要求该范围补银行流水或登录网银。保留原银行证据状态为空/未覆盖，不伪造实际银行日期、银行行或银行验证完成数。此例外优先于下文及历史参考记录的一般银行验证要求，直到用户变更规则。

有此例外时，首页先列“总数＝银行已验证＋用户规则通过＋仍待核”；通过合计与银行验证数分开。默认通过不再计入业务待办，但实际银行验证率仍只用银行已验证作分子。2026年9月在10月11日完成追加取证后的历史结果为83＝75＋8＋0；原47项已按43批次核对。历史数字不是以后月份的默认值。

1. 用户指定月份优先；未指定则以上一个完整自然月为主账期，在开工更新中说明。当前日期按聊天客户端时区；各平台日期保留其原时区，必要时另外规范化。不要因旧技能写了澳洲时区就改掉用户的当前时区。
2. 同时纳入：目标月应结算/实际发出的平台款、目标月银行入款、目标月退房但尚未打款的订单、以前月份尚未结清的差异。查询延伸到实际执行日，追踪月末打款的次月到账，按实际结算周期继续向前追查。写明数据截止日，不能声称已经检查未来日期。
3. 分别保留订单入住/退房日、平台收款日、打款发出日、预计到账日、实际银行交易日、飞书记账月份。**飞书的退房月份不是银行到账月份。** 对跨月款做连接说明，不改写原月度口径。
4. 按平台、账号/法人主体、房源、币种、收款银行尾号建立覆盖清单。检查目标期间有业务的账户，包括已停用但仍有历史应收款的账户。不能把当前浏览器的一个账号当全平台。
5. 先读 [references/account-map.md](references/account-map.md) 和 [references/account-inventory.md](references/account-inventory.md) 获取已核实入口与账户清单，每次从飞书刷新。用户估计4个Airbnb、2个Booking和2个Vrbo，并说明数量大概、密码在飞书；2026-10-10实际表内有4个Airbnb、3个Booking、4个不同邮箱的Vrbo线索，以及额外合作业务QuickBooks。数量均为核查线索，不是固定上限；不能排除估计数量以外的账号。Guesty的3个启用Stripe处理商也不代表Stripe切换器的所有账户。
6. 若打款直接进入房东、合伙方或其他公司账户，先核实收款权属和账户覆盖；不得因为用户当前QuickBooks银行没有该笔款就报漏款，也不得无银行证据判定对方已收到。
7. 客人欠款核查除退房月清单外，补查目标月在住、跨到次月退房的确认订单，以及银行发现的线下住宿发票。区分目标月到期分期与未来款项；客人名单写明实际覆盖口径，不把退房月样本称为所有住宿。

## 获取证据

默认使用 Codex 内置浏览器及已有登录。用户明确指定 Chrome 才按本机 chrome-task-recovery 技能操作。实际读到页面后判断登录状态；连接失败不等于退出登录。

需要账号资料时，在飞书 `民宿管理表 → 所有账户` 按用途定位；读取本次必要资料，不批量导出密码库，不将密码、验证码、密钥或完整卡号存入技能/报告。切换账号后核验身份和所属公司，再下载；不能把不同账号的数据混名覆盖。验证码等人工关卡集中说明并继续其他可做部分。

优先原生导出或已有只读连接器；没有接口时用受支持浏览器读取。每份证据记录平台、账户、导出时点、日期口径、筛选、币种、记录数及实际覆盖区间。核查分页/滚动加载及导出行数；只读到可见几行就标“样本”，不能报全量。加载中出现旧行数/旧结果时，等目标数据完成后再采信。

### QuickBooks / 银行

- 核实公司与各银行账户；区分连接银行的流水与 Direct Booking、settlement funds 等账面/清算账户。账面余额、收入报表、手工 Deposit、已分类标签不能单独证明银行到账。
- 读取目标银行的 **Pending、Posted、Excluded** 原始银行交易及相关退款/退回/冲正。不因已经Post、已有自动规则或被Excluded而漏读，不实际执行匹配动作。
- 本机新版QBO的“Export to CSV”只导出当前页，须逐页导出并核对总行数。下载事件超时不等于没有文件：先核对本机下载结果和表头，避免反复点击。虚拟列表可见16行不能代表全部页面。
- 保留银行账户、日期、币种、金额方向、完整原始描述、银行参考号/交易ID、QBO状态。跨视图和重复导出按真实交易ID去重；没有ID时保留歧义，不能按同额同日擅自合并两笔真实流水。
- 核查feed最新交易日、连接警告、数据缺口；刷新时间近不代表期间完整。可用时与原银行对账单核对覆盖。缺银行账单或feed中断时明确限制，不能把查不到定性为平台未付。
- 银行入款中识别经营收款、管理费、赔偿/补收、退回付款、退款回流、贷款/注资和内部转账。先列事实，分类不明保留待核，不把全部正数视为住宿收入。

### 平台 / 支付处理商

按 [references/platform-reconciliation.md](references/platform-reconciliation.md) 逐个平台处理，建立：

`订单及应收 → 客人实际收款/平台代收 → 手续费、退款和调整 → 净打款批次 → 银行入款`

Guesty用于订单、来源和支付关联；实际资金可能经Stripe或预订平台结算。**同一笔 Booking订单在Guesty和Stripe出现，只是不同阶段，不能算三次收入。** 对每条资金路径选定实际打款方，保留其他系统ID作桥接。

## 匹配与判断

1. 先按币种、法人/收款主体、银行目的账户限定候选，再按打款/银行参考号、净额、时间和订单组成匹配。银行摘要别名（例如 Payoneer）需从实际打款证据确认，不能靠QBO类别倒推。
2. 一对一匹配优先。同额和相近日期只有候选意义；没有共享参考号时，需核实收款账户映射、付款方身份、唯一候选及实际结算时间，并标明证据强度。银行摘要中的付款方尾号不能误作用户收款账号。
3. 合并打款或拆分到账使用批次明细分配。一笔银行款可以有多个有依据的分配，但累计不得超过银行金额；一笔平台款也不得重复占用两笔银行款。禁止凑任意金额组合“对平”。
4. 用十进制定点金额或最小货币单位计算。默认精确到币种最小单位；差一分钱也保留，只有来源证明的舍入/手续费/汇兑才可解释，不设置任意百分比容差。不同币种不直接相加；换汇保留原币、结算币、实际汇率和费用。
5. 平台明细的带符号组件之和应等于净打款。佣金若另开票另扣，不能又从打款扣一次。退款、拒付、准备金扣留/释放、负余额抵扣、取消费、长住分期、共同房东分成逐项桥接。预授权和可退押金不当已结算住宿收入。
6. 反查每笔银行入款是否已有来源；“银行已收到但来源未知”与“平台已付但银行未找到”分开报告。继续追踪打款失败、退回、冲正；曾显示paid或曾入账不代表最终留存。
7. 与飞书月度记录只读交叉检查，指出漏记/重复/期间差异；不能用飞书已录金额替代平台和银行证据。不要把同一订单合法分期删掉，也不照搬月度记账技能对完全相同候选行的录入规则来重复统计到账。
8. 可以复用此前记账任务已经下载的原生平台报告，先核对法人、银行、日期范围、批次与父子行控制，并记录原下载日。本轮登录未成功仍如实写明，历史报告不冒充本轮最新导出。缺口仅补查原报告截止日至本次执行日的变化。退款支出必须继续搜同参考号的正数退回，飞书已录负数不能证明客人最终收到。

用户2026-10-11进一步明确：已有账号和可下载平台明细时，必须自行继续补取证据，把合并/分期组成与QuickBooks实际流水核对，不能将“候选待匹配”作为可做工作完成的替代品。Airbnb至少保留父批次与每条带符号订单组件；对目标未结项打开打款详情及发放时间，下载完整字段，检查所有同额候选和跨月款。无共享参考号并不自动否决匹配：在账户/币种/净额/发放窗口、付款方交叉证据、全量唯一分配、组件控制及退回检查均充分且一致时，可明确标为“综合证据匹配”，与直接共享参考号核验区分。不能仅凭Payoneer名称、同额、自动分类或任意凑数升级。确有歧义则指出具体缺口，继续可做的独立核查。

每笔采用以下结论之一并写依据：

| 结论 | 适用条件 |
|---|---|
| 已匹配银行到账 | 实际银行入款、主体/账户/币种与打款链均有充分依据，并检查相关退回/冲正 |
| 用户规则通过（银行未验证） | 仅APEX / 19 Lugano，核实平台或Stripe已实际转款；保留转款ID与原始证据，不要求4484银行流水 |
| 候选匹配待核 | 有同额或其他线索，但账户、批次或唯一性未证实 |
| 正常待结算/在途 | 有平台预计打款/到账日或明确结算条款，截止日尚未超期；银行未证实时不写已到账 |
| 到期未见银行到账 | 预计日已过且目标银行范围完整，仍未找到；描述为待追查，不断言资金丢失 |
| 平台尚未收齐/未打款/失败或退回 | 按平台实际状态分别列明缺口；未提供可靠到期日则标待核，不自行造逾期天数 |
| 金额差异 | 仅部分到账，或净额与银行金额不符且没有完整解释 |
| 银行入款来源待核 | 有银行证据，尚未确定订单/打款/其他用途 |
| 数据不足/未覆盖 | 账号、银行或期间资料缺失，单列缺口 |

## 交付与完成标准

按 [references/report-contract.md](references/report-contract.md) 生成中文摘要、逐笔打款到银行明细、双向差异清单、覆盖清单和证据索引。普通查询可在聊天答复；整月对账将用户成果放到当前工作区 `outputs/`，中间处理放 `work/`。金额较多时提供可筛选Excel并使用可用的电子表格技能。

- 报告首页和聊天答复必须先写“纳入核查Y项，银行验证完成X项，用户规则通过P项，仍待核Z项”，四项满足Y=X+P+Z；无规则通过时可省略P。明确总数、已验证数、待核数、已发现问题数；不能只说“已查Y单，未发现欠款”造成全部完成的印象。按退房月确认订单、跨月在住订单、线下发票分组列出总数与进度；原始取消、询价、拒绝记录的数量和排除口径另列。
- 每项使用互斥的验证进度：银行验证完成、候选对应待核、缺银行资料、尚未查等；所有进度项数必须合计为纳入总数。有平台收款或同额银行候选，不计入银行验证完成。已查过页面不等于验证完成，账号登录成功也不等于该账号整月完成。
- 随后给出客人欠款结论与具名清单：已证实欠款、仍有证据缺口、系统显示欠款但已实收分别列示。每个客人连接订单应收、实际收款、费用调整及QuickBooks银行原始行。未完成项欠款金额留空并注明待核，不用0占位；“暂未发现已证实欠款”须紧接未完成项数，不能改写为总欠款0或全部无欠款。
- 已发现问题按类型计数；说明系统余额未同步等问题是否已包含在已验证订单中，退款事件、取消记录、管理费等是否属于不同范围或与订单重叠。订单数、打款批次数、银行行数及问题事件数分别统计，不互换、不跨层级相加。多个备选银行行的金额不得合计成该订单/批次的已收款。
- 用户明确QuickBooks有两个登录账号：Startrise与George合作的KEWARRANEST必须分别列示，不能只写“QuickBooks已登录”。每轮展示账号/公司、已连接银行名称及尾号、已取流水行数与截止、当前是否可访问、最后成功登录时点、是否需要重新登录及由谁补什么。历史已取报表、当前登录会话、银行验证完成三个状态分开；切换/过期不抹掉已取资料，也不能说全部账号同时在线。
- 单列银行缺口表，将仍待核订单按实际收款银行汇总，合计须与待核总数相等；另外列APEX用户规则通过数，不再计为待补流水。分别说明“银行已有入款但来源/批次待核”和“目的银行尚无流水”。未知尾号保留未知，不把Startrise的ANZ Transaction猜成APEX的4484。非豁免范围需要用户提供网银/其他账套入口或既有账单路径时准确点名公司、银行尾号、期间及影响项数；現有凭据可自行使用的账号不要让用户重复提供密码。
- 各平台未结项滚动至下次，以平台账户+打款ID或明确订单分期ID保持稳定；重复运行更新原差异，不生成重复异常。保留首次发现、上次状态、本次证据和结清日。
- 每个异常给出平台/账号、房源或订单、金额币种、应到账日、已查银行/区间、缺失环节、证据及下一步。没有证据的日期和原因留空说明。
- 仅当目标范围完整且双向匹配与金额检查通过时说“本月已核对完成”。样本核验、缺任一应查账号、分页不全或银行范围未完整时，结论必须带覆盖限制。
- 恢复本次临时搜索/筛选，保持业务记录不变。最终说明已核查、未核查和真正需要用户处理的环节。
- 创建“月度技能”本身不等于安排定时执行。用户明确要求排程时再使用当前自动化工具，依据已确认日期、时区和通知对象设置，不擅自照搬旧技能的7号时间或收件人。
