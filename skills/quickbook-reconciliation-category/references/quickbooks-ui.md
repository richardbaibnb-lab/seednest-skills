# QuickBooks Pending操作与核验

本参考记录2026-09网页上观察到的行为，产品可能变化。优先使用已授权的目的明确的接口；走浏览器时按当前工具文档操作，不采用旧标签页ID、旧AX编号或未观察过的选择器。

## 定位当前工作面

- 从当前应用/浏览器清单定位真正使用的QuickBooks标签。曾出现旧标签已logout/断网，但另一标签仍可用，不要仅据旧标签宣称全站失联。
- 验证公司、银行账户、Pending状态、筛选、页数及金额方向。用户正在填规则或编辑未保存草稿时，不关闭或保存其草稿；先做本地查询，待完成后重新读取交易集合。
- 用户同时Post、规则Auto-post或刷新会改变数量。先按最新集合建基线；本次无操作的变化不能写成助手成果。
- 在修改前尽量设置便于审阅的页面范围和Full bank description；不把全选、批量Post或规则创建当作分类保存方式。

## 选择Category

- 以银行参考号＋日期＋金额（或真实交易ID）定位行；同人多笔或同日不同金额分开核对。
- 页面显示的Category可能是占位按钮，点击后才变成实际combobox。第一次点击的超时或节点替换不等于失败：重新读状态再继续，不盲目重试导致改错行。
- 同一类别可能同时出现在Suggested和All accounts。选择准确名称及科目类型，特别区分Direct Booking（Bank）与Direct Booking (this one)（Income）。
- 大表使用虚拟行，滚动后索引和渲染行会变化；按新状态重新定位。不要依靠旧屏幕坐标或快速长循环批量点选。
- 只选Category并核对结果，不点击Post、Match、Exclude、Create rule。发现应该配对既有凭证时，记录凭证和金额给人工处理。

## GST：不可只看输入框

改Category可能自动给原本空白的GST填入GST on purchases（10%）等默认值。曾发生：清空combobox并Tab离开后画面看似空白，CSV仍保留10%，行重新渲染后也恢复。

因此：

1. 保存修改前税项，改完读实际行和原生导出/接口记录。
2. 有可靠本期票据和税务依据、且用户授权范围涵盖税项时按依据处理；否则准确说明自动带入或待核状态。
3. 不用0%、GST-free或Out of Scope假装等价于未知/空白。用户已明确的水费No GST/GST Free应按相应零GST税码填写；这与未知税项不同。不能保持原状态时，把实际差异列给用户，在此技能下保持未Post。
4. 审核报告不得只凭输入框清空成功便写“GST未变”。

保险尤其不能接受Category自动带出的整笔10%。即使税码名称正确，仍要核对invoice实际GST金额与QuickBooks计算结果，stamp duty等非GST部分不得混入应税基数；界面不能准确准备时，列出原票税额和需要人工处理的差异。

## 分类选择的持久性

### 2026-09-14退款税码报错补充

用户尝试Post后，本批13笔供应商退款出现“error while calculating tax”。这些行的原生CSV仍写GST on purchases，但页面税码为空。打开退款行GST下拉框后，存在购买及销售两类税码；重新选择明确标为“GST on purchases (10% Purchases)”后，页面恢复有效选项，该行报错消失。没有Post，也没有为了消除报错换成销售GST或0%。

支出行当时使用名称“GST on purchases (10%)”和“GST free purchases (0%)”，退款行则有“(10% Purchases)/(0% Purchases)”后缀；按当前实际选项读取，不硬编码一种名称。修复这种无效选择可能不在原生CSV文字差异中体现，应同时记录页面报错/选中状态变化。重新绑定原税码只修复UI状态，不证明退款原单及税额已审计。

曾测试过新版/旧版、行内选择和Bulk Edit Apply：未Post的Category在刷新、翻页或导航后还原。不能把Bulk Edit Apply当作已入账或必然服务器保存。

尽量在一个可审阅页面完成、仅安全滚动，导出当前选择并留在该页。不要反复切换版本重新测试历史问题，也不要通过自动Post、新规则或另建Expense来保住选择。若产品已支持真正保存草稿，则核实保存结果并使用现有授权范围内的能力。

## 前后核对

运行 `scripts/compare_exports.py` 可得到：新增/移除键、重复键、Category/GST/From-To等字段变化和汇总。该脚本不访问QBO、不更改原文件、不证明分类或GST正确。

- 正常仅选择Category时，日期、金额、对象、交易集合应保持；GST联动是单独需披露/解决的变化。
- 有重复描述/日期/金额，不能按出现顺序可靠判断具体改了哪一笔；补真实交易ID或原始凭证再判断。
- 导出与页面都可能在同时操作时变旧；报告写明实际核验时点和用户同步操作，不据账户卡片余额差额臆算完成数量。
- 交付给用户的结果以准确分类、明确未决项和人工Post为终点，不把“能在UI里点完”当作全批账务已经核准。
