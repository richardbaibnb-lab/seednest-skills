# 新airbnb上架

创建或续填时，把用户提供的新房源资料实际填写到指定 Airbnb 账号，完成可复核的草稿；只写文案或列操作建议不算完成。用户希望首次边做边确定规则，以后逐渐完善并自动填写。命名默认每次提供“SEEDNEST取名”和“同区域取名”两套方案供用户选择。用户仅要求取名时，只交付命名方案；用户要求“我调整好了，看看我改了什么、学习一下”时，执行下方“手动修改后的复盘”，不继续按旧记录填写。

## 已确认的完成标准

- **默认填好并保存草稿，等用户确认发布。** 这是用户在 2026-09-17 明确选择的流程；“自动上架”“按以前规则做”本身不取消这个偏好。
- 准备、上传照片、创建及更新草稿已包含在用户委托内，不逐步索取许可。
- 发布确认应对应具体房源及完成后的草稿。已明确批准该草稿发布且关键条件未变时，执行发布，不重复询问。
- 当前请求只要求创建或改进本技能时，只维护技能，不进入账号创建真实房源。

## 启动与已有进度

1. 读取 [references/rules.md](references/rules.md)，再读取目标账号已有的规则文件（如果存在）。当前明确指示优先于历史规则；区分本套房源例外与长期规则。设施填写必读[616修订标准](references/amenities-standard.md)；代管描述必读[19号描述标准与原文](references/managed-description-standard.md)。
2. 从对话提取图片文件夹、完整地址、目标账号及本次命名要求；已有内容不重复问。未指定命名方式时直接准备两套方案，不先要求用户选方法。尚缺账号时先整理本地资料，不能默认使用当前登录账号。
3. 找到本次房源已保存的草稿或进度。检查本技能 `state/listings.json`（存在时）及目标账号实际房源列表；按账号、含单元号的地址和已有链接匹配，不只比较标题。
4. 有明确匹配草稿就续填；已发布或多个疑似匹配项时先核实创建意图。新草稿生成后立即记下链接/ID，再继续填写，避免中断后重复建房源。

## 工具和账号

- 优先使用当前可用且支持实际 Airbnb 操作的正式连接器；否则使用可用浏览器操作工具。浏览器执行前读取已安装的 `computer-use:computer-use` 技能及工具文档，按照当次能力操作，不预设存在 Airbnb 专用工具、上传接口或固定页面选择器。
- 在目标浏览器会话核对账号显示身份和房源列表，与用户指定账号对应后再写入。账号别名相似或同一账号包含多个可选房东身份时，核清本次房源归属。
- 账号缺失、登录失效、验证码或身份验证时，请用户完成必要步骤；继续整理不依赖登录的资料。不得把登录受阻误报为草稿已保存。
- 只操作本次房源，不改其他房源、收款设置或账号全局设置。参考房源只读。

## 照片与房源事实

1. 查看用户指定文件夹内的文件并实际查看照片；按需查看文件夹内用户提供的户型图或说明。保留原文件，不把文件夹名当作已证实地址。
2. 为每个拟上传文件记录原路径、所属空间、用途、顺序和是否上传；根据实际画面去重，剔除明显失败照片、无关截图及暴露私人信息的图片。若文件夹含多套房源，先确认归属。
3. 按客厅、卧室、厨房、卫浴、户外等实际空间组织照片，选择清晰且能代表房源的封面；每个卧室组的第一张必须优先选能看到完整床的全景/广角照，床头、床品及装饰特写放后面。逐间检查首图，不能只检查整套房源封面；没有完整床照片时使用现有最完整视角并注明缺项，不合成画面。不足以区分的卧室不要擅自编号成多个房间。未经要求不生成虚构实景或改变设施的图片。
4. 建立本次事实表：字段、值、来源、状态（已证实／待确认）。照片能证明可见物品，通常不能单独证明完整房间总数、床垫尺寸、最多入住人数、独享范围或设施可供客人使用。
5. 按 [references/field-guide.md](references/field-guide.md) 核对事实与设置。未知不等于“没有”，不能为通过页面校验而填猜测值或占位价格。

## 同账号参考与首次沟通

- 优先参考用户指定的同账号房源；未指定时选择少量、通常两三套相近房源，记录链接及读取日期。账号没有可参考房源时，根据真实资料起草并与用户建立规则，不自行跨账号套用。
- 代管房源按用户指定的[19 Lugano Avenue模板](references/managed-description-standard.md)，结构、语气和措辞尽量接近原文，仅替换必要的房源事实；通用注意事项直接复制，不改写。其他房源提取参考的语言、语气、段落组织、品牌介绍和通用服务措辞，写成适合本套房源的简介。标题按下方“双方案取名”执行；同账号参考不限制“同区域取名”读取其他房东的公开可比标题。
- 不能把参考房源的床数、景观、车位、设施、距离、价格、入住方式或特定承诺当成本房源事实。参考房源现有的经营设置是候选规则，未经用户确认不得升级为账号通用默认值。
- 第一次使用该账号，边完成已知内容，边把真正缺少的信息和候选规则集中成少量问题，注明推荐依据及影响。避免要求用户重新提供已能核实的资料。
- 不把规则确认做成固定仪式。用户先前已经说清的规则直接执行；只有不确定、冲突或新出现的必要字段才询问。有异步提问能力时继续做独立工作，未获答复不能视作默认同意。
- 用户确认或纠正后按 [references/rules.md](references/rules.md) 保存适用范围。单套例外只记本套；不要仅因用户没有反对就保存为长期规则。

## 双方案取名

- 原有命名方式正式称为 **SEEDNEST取名**，保留 [Seednest 命名规则](references/seednest-naming.md)。新增命令 **同区域取名**，按 [双方案与 AirDNA 参考流程](references/naming-options.md) 读取同区域、相似房型中收入靠前房源的标题，提炼可能的预订动机，并结合本套真实卖点生成另一套名字。
- 每次为新房源取名或重新提名时，默认并列交付两套完整候选标题、中文含义与命名理由，供用户选择；不能自行把其中一套当作最终决定。用户本次明确只要一种、直接指定最终标题或已选定同一套标题时，按其指示执行，不重复选择。
- 选名期间继续照片、事实核对和其他可独立完成的草稿工作；写入标题前取得用户对具体标题的选择。单独取名不要求先创建 Airbnb 草稿，也不修改现有房源。

## 实际填写与保存

1. 以当前 Airbnb 页面真实顺序、字段名称、长度限制和选项为准，逐步填写房源类型、位置、空间配置、设施、照片、标题、介绍及当次流程要求的设置。字段清单用于查漏，不是假定页面永久不变。
2. 地址拆分到正确字段，尤其核对单元号、街道、城市、州、邮编和地图标记；位置有歧义时先查清。不要把精确门牌或门禁信息写进公开营销文案。
3. 上传后核对实际照片数量、预览、封面与顺序；平台支持房间分类或图片说明时按真实空间填写。上传失败时核实已成功部分，再补传缺项，不重复上传全批。
4. 每完成一段检查是否保存成功。采用页面显示的保存反馈、重新打开字段或草稿状态验证，不能仅凭点击按钮推断保存。
5. 尚缺关键事实时，保存已经完成的部分，并明确列出剩余字段。若流程强制提供尚未知的数据才能继续，停在该步，不虚构值；仍完成可独立完成的照片整理、文案和问题清单。
6. 遇到组合按钮（如同意并发布、上线并开放预订）先判明效果，默认不点击。不能为了完成草稿而越过用户的发布确认。
7. 区分当前创建向导可填写的项目与平台明确留到发布后配置的项目。后者记录为后续事项，不要求用户为完成当前草稿提前补齐所有未开放字段；不能为了访问这些设置而发布房源。价格页继续之前，单独核对周末调整；折扣页核对勾选状态、比例、适用天数和是否叠加，不仅记录基础价。

## 草稿交付与确认后发布

- 从草稿页面回读，核对账号与房源归属、地址、照片、标题简介、人数和床型、设施、费用及币种、日历和预订设置；区别平台自动值、账号已确认规则和本套指定值。
- 给用户简洁的中文交付：目标账号、地址、标题、草稿链接、完成状态、影响费用或接单的主要设置，以及仍需确认的内容。明确写“草稿，未发布”；未填完时写“部分草稿”，不能声称可发布。
- 需要发布决定时，在草稿具体、可复核之后再提问。说明等待发布确认源于用户已保存的“填好并保存草稿，等我确认发布”偏好；用户本次只要草稿时交付即可。
- 用户明确批准本次草稿后，检查批准后是否变更了价格、开放日期、容量等关键条件，再执行发布。只在关键条件改变或批准对象不清楚时补充确认；发布后核实后台状态和房源链接，区分已提交审核与已经上线。
- 发布或保存返回不明确时，先重新读取房源状态与列表；发现已经成功就接续后续步骤，不能盲目重试创建或发布。
- 每次结束更新运行记录。仅在用户提出长期规则或确认候选规则时更新账号规则，并简短说明本次记住了什么。

## 手动修改后的复盘

1. 从本技能进度索引确定同一账号和同一草稿ID，读取之前的事实表、文案、照片顺序及回读记录。当前页面优先；不要把旧草稿重新写回去。
2. 只读检查当前各页及最终预览，不改字段、不重新上传、不触发发布。优先直接打开此前实际观察到的编辑页；必要的界面导航保留用户现值，遇到会新作声明或改变设置的动作就停在已能读取的位置。
3. 分类比较：有旧值的明确变化、已有基线且未变的内容、没有旧快照的当前配置。没有旧值时，不声称某个勾选是用户新增；平台实时推荐价也不能算作助手先前确定的房价。
4. 用户称已调整完成，只能佐证其本次修改意图；未变化的默认数字、未勾选披露或尚未出现的字段仍需按各自证据判断，不能统一当成已确认。若用户要求学习其手动修改，且旧值与新值对比证实某字段已被实际修正，并在最终预览一致显示，可作为本套房源的用户修正保存，移除被解决的旧待办，不反复要求同一确认。最终预览中的卧室/卫浴、床数、人数与事实表不一致时明确指出，复盘时不擅自修改。
5. 将本套事实与费用保存为有日期和来源链接的案例，并从对应账号规则文件链接过去；将可复用的文案风格、检查顺序和实际操作经验写回技能。只有明确适用于账号或以后房源的经营偏好才升为默认；单套房价、折扣、房间数和安全披露不外推到所有房源。
6. 向用户说明实际改动、学到的规则和仍存在的差异；同时更新进度索引，移除已由当前页面解决的旧待办。再次复盘以上一次回读为比较基线，保存最新有效值和带次序的历史，不让旧折扣或旧标题继续出现在当前规则中。保持未发布状态，不把这次复盘理解为发布授权。
