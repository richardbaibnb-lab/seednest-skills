# OPERATION-3日未付款订单检测

## 范围及已获授权

- 用户于 2026-10-07 要求创建每天运行的检查：发现未来三日内入住但未收款的订单，立即通过飞书提醒 Sabrina，并通知用户。随后明确取消微信，改为醒目的 Codex 通知。此授权覆盖该流程后续重复运行，不逐次征求发送许可。
- 默认以 Guesty 中 Richard Bai / Startrise Management Pty Ltd 的有效订单和实际收款记录为依据，检查全部房源的非 Airbnb 订单。此数据源为建立时的已披露默认，用户后续指定的数据源/到账口径优先。
- 用户于 2026-10-07 更新：**Airbnb 订单默认 OK，直接排除**。识别真实订单渠道/来源为 Airbnb 后，不再检查付款明细，不新增订单记录，不列入报告、待核实清单、笔数或金额合计，也不向 Sabrina 或用户提醒。已有 Airbnb 记录退出当前跟踪及补发队列，不将此操作记作实际已付款；此前已经发出的消息及历史快照保留为历史。仅用户以后明确改变范围才重新纳入。
- 排除依据是真实订单渠道/来源，不是付款处理账户名称。例如 Booking.com 或 Trip.com 订单的 Stripe 账户叫 `zh.airbnb`，仍属于本流程检查范围；渠道不清时先核实，不能凭订单号或账户名猜测。
- 默认窗口为检查时刻起未来 72 小时；用房源当地时区解析入住时间，正确处理夏令时。纳入已确认且尚未实际入住的订单；排除已取消、拒绝、询价、测试记录和已入住订单。当天已过预计入住时刻但仍未办理入住的也补查，明确标注例外。
- 仅检查及内部提醒，不扣款、退款、改收款状态、改付款计划、取消预订或给客人发送催款。不读取卡号、银行凭据或私有应用数据库。
- 用户于 2026-10-08 强调正常订单不得混入预警。扫描记录与预警清单分开：正常平台代收、正常未到期计划和已付订单不进入预警笔数、金额或消息；没有异常证据时，不因资料为空而要求 Sabrina 逐笔排查。
- 默认用 Codex 内置浏览器，保持后台且复用登录；只有用户明确指定 Chrome 才使用 Chrome，并先读本机 chrome-task-recovery 技能。
- 用户于 2026-10-09 明确：Guesty 出现登录页时自行点击 **Continue** 恢复登录。沿用页面记住的账号和浏览器已填入的密码，正常登录步骤无需再确认；不要读取或展示密码。等页面加载及自动填充后，再点击当前步骤的 Continue 并核对结果；仅在确实缺少凭据、出现短信验证码或其他无法自行完成的验证时请用户处理。不要仅看到密码页就认定必须人工登录，不反复提交失败的登录。

## 每轮先做运行门控

读取 [入口、通知及状态](references/operations.md) 中的固定状态文件和本聊天上下文；保留已有运行结果，不初始化覆盖。

1. 用户已接受同一聊天每 15 分钟唤醒，Codex 可用后尽快检查；当天完整成功检查后跳过重复全量扫描。日界线使用用户时区 Asia/Shanghai。它不是 Windows 开机事件触发器，不保证开机瞬间执行，也不保证 Codex 未运行时执行。
2. 当天已完整扫描且无未完成发送时，安静结束。用户明确要求“现在跑一次”时重新检查，不受当天完成门控限制，但仍对通知去重。存在未完成发送时，只重新核实待发订单和补发失败渠道，不重发已确认成功的渠道。
3. 失败/部分覆盖不能记成“检查完成”或“没有未收款”。暂时故障可下次唤醒重试；需要人工登录或权限处理时记录阻塞，状态未变时不反复通知。
4. 不改 Windows 启动、通知或安全设置；调度必须通过 automation_update 工具创建/维护 heartbeat，优先更新本流程已有 ID，不创建重复任务。

## 检查及付款判断

1. 核对登录账号，刷新订单。先按真实订单渠道排除 Airbnb，再按入住时间覆盖整个窗口、全部房源和全部分页。记录过滤条件及非 Airbnb 范围内的订单总数、已核查数；不能把屏幕可见的几行当全量结果，也不把排除的 Airbnb 逐笔落盘。
   - 优先从 `Source` 栏识别真实渠道。2026-10-08 实测 `Platform` 勾选除 Airbnb 外所有选项仍漏掉 `tripCom2`，不得将此筛选结果当作完整范围；用日期范围内全表的真实 Source 排除 Airbnb。
2. Guesty 的 Upcoming unpaid reservations、Balance Due 等只用于筛选候选；读取订单详情、渠道、付款方、Payments/收款交易、退款、付款计划与失败记录后作判断。平台的系统视图可能遗漏自收款渠道或把平台待结算当未付，不可仅凭视图标题下结论。
3. 每笔候选保存：订单 ID/确认号、详情链接、房源、客人姓名、渠道、入住时间及时区、应收/已收/剩余金额和币种、交易/付款计划状态、核实时间及证据摘要。不存付款凭据或无关客人资料。
4. 分类必须区分：
   - **确认未收/部分未收**：已核实本方承担收款责任、款项按约定现在应收或须在入住前收齐，且实际记录支持有效余额未收，或有明确失败/逾期证据。仅 Guesty 没有记录不够断言客人欠款；线下到账或平台代收尚未排除时降为待核实。只把成功到账/完成且未退款的交易计为已收；预授权、scheduled、pending、processing 不算已收。部分付款仅列剩余应收，不把原订单全额算作未收。
   - **已安排、尚未收款**：有效未来付款计划覆盖应收，按约定在付款期限内正常执行，静默记录，不进入预警。未到期不等于已收妥，也不是逾期。只有失败、已过明确到期时间、计划金额不足或违背已知入住前付清约定才预警。
   - **平台代收/结算中**：明确由渠道处理且无失败、逾期或金额缺口证据的，静默记录。Booking.com 处理、Channel/Scheduled、On track 的订单，不因 Guesty 显示 Not paid、Total paid 0、Unscheduled 或日期 `—` 进入预警；这些字段可能尚未同步或确认，不能代表客人未付。正常延后结算不算风险。仅在已知应结算日期届满仍未收或有明确异常时，单独称“平台结算异常”。未核实平台/银行流水时，不写“客人已付”或“银行已到账”。
   - **待核实**：必须同时存在具体收款缺口信号，例如临近入住且 Pending payment collection、无成功收款及无覆盖余额的有效付款计划，或相互矛盾的收款责任。先核对正常平台代收、VCC 激活时间、约定付款期限、人工收款记录等解释；无法排除时只列黄色“收款待核实”，写清尚缺的证据，不算入确认未收合计。仅 Balance Due、字段空白或不知银行是否到账均不足以产生提醒。
5. 押金/预授权和住宿费用分开。未到付款期限、平台代收待结算等保留真实原因，不凭总额自行催缴。不同币种不直接相加。
6. 遇到明确风险立即准备通知，不必等全部订单完成；可以小批合并，优先当天入住、24 小时内入住及扣款失败。发送前刷新该订单，已收齐/取消/移出窗口的撤出待发。

## 通知及去重

- 飞书只发已核实的 Sabrina 单聊。通知中文，写明房源、订单号、客人姓名、入住当地时间、币种及金额、具体收款状态、订单链接，请她核实/处理。事实与待核实项分开；不发卡号、证件或无关截图。
- 通知身份已明确且动作在原授权内时直接发送。发送前记录 pending/sending，发送后回读聊天确认消息存在才标 sent。返回不明时先查聊天，确认未送出才重试一次；仍不明保留 uncertain，停止盲目重发。
- 独立追踪飞书和 Codex 的通知。新风险、未收金额或付款状态的实质变化、从大于 24 小时变为 24 小时内、首次进入入住当日等才产生新的通知版本；同一状态不在每次唤醒或每天重复轰炸。已收齐关闭记录；以后再次变为未收时开启新版本。
- 以上紧急程度升级仅适用于仍有具体风险的订单，不将正常代收/正常计划因接近入住而重新拉入预警。复核发现历史提醒依据不足时，保留历史发送记录，撤出当前预警并向已通知的接收者发送一次明确更正；撤警不等于确认付款成功。
- 即使飞书失败，也立即在 Codex 醒目报告真实风险并注明“飞书未发送成功”，不得等成功才告知用户或谎称 Sabrina 已知悉。无异常时保持安静，检查不可用时只在首次或阻塞变化时通知。
- Codex 通知用粗体首行 **🚨 入住前未收款｜N 笔需处理**；当天入住加 **🔴 今日入住**，其余按紧急程度排列。列出房源、入住时间、未收金额/币种、明确状态和飞书发送结果。待核实用 **⚠️ 入住前收款待核实**，访问阻塞用 **⚠️ 未收款检查未完成**。不得把不确定金额算入确认未收合计。
- 保持自动化通知开启（notificationPolicy 为 null）。醒目标题不代表可以强制系统弹窗、声音或置顶；这些取决于用户的 Codex 和 Windows 通知设置。

## 完成及报告

完整核查后保存当天扫描完成时间、覆盖数、发现数及每个渠道的发送状态。一个渠道失败不撤销完整扫描，但保留其待发队列。仅用户明确停止时停用监控；订单个别关闭不停止整个流程。首次建成时准确区分技能已安装、定时已启用、入口已验证、全量试跑已完成，未做的不能宣称成功。
