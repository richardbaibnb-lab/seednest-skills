# 核对、运行状态与每日调度

## 现场证据、发票与采购行

每个收货事件记录：平台/群、消息ID或时间与上下文、原图文件、房源、物品及规格、确认数量/单位、对应发票文件和行、采购记录ID/编号、更新前后状态、异常。证据不齐的记录待核实，不猜整箱内容。

| 情形 | 处理 |
|---|---|
| 发票或订单写已购买，群里无收货证据 | 只支持已下单，保留原到货状态 |
| 物流显示Delivered，但群内未确认本房源实收 | 保留物流线索，不能仅据此标现场已到货 |
| 群明确收到某编号/规格及数量，或照片与上下文能唯一识别 | 匹配准确采购行及订单，累计该房源真实收货量 |
| 图片只显示纸箱，没有品名/规格/数量 | 归档为待识别包裹，待核实，不推断整个订单到货 |
| 国内仓库/转运仓照片或“到仓” | 记录中转进展，不算房源现场收货 |
| 买4把椅子，确认收到2把 | 记录2/4，使用现有部分到货选项；不得标全部到货 |
| 图为参考效果图、旧图、退回商品或转发别处到货 | 不计新增收货；必要时保留上下文线索 |
| 同一照片跨群转发或多角度拍同一件货 | 一个收货事件，可有多张照片；不重复累计数量 |
| 数量足够但损坏、错规格、缺配件或待退货 | 记录实收及异常，不把“已到”解释为可用/验收通过 |
| 名称相同但床型/尺寸/颜色/商品款式不一致 | 不能仅按名称匹配，保留待核对 |
| 多地址共用一行 | 只统计本地址分配量；字段若对整行生效，不用本地址到货覆盖整行其他房源状态 |

一条消息的“今天又到2个”与“目前已到4个”分别表示增量和累计。保存原话、去重后再计算，不能把累计汇报每次相加。购买包数、单包数量与实际件数统一口径后比较，套装/分箱不能用包裹数代替采购数量。

照片缺失但线下人员明确、可信地报出物品与数量，可作为收货证据并标记待补照片；有图片但规格/数量无法确认，也不能把图片存在视为全部到货。发票缺失不抹掉已经证实的收货事实，但要保留无法完成三方核对的原因。任何模糊的行匹配先留待核实。

## 照片归档

- 先检查准确父目录内是否已有`setup货品照片`，并保存其真实链接/ID；只在不存在时新建一次。创建结果不明时重新查找，不连续新建。
- 优先取得群内原图/可下载媒体；只能截图时注明“群图截图”，保留足以识别物品的内容，不用缩略图冒充原图。缺失/失效图片列为待补，不编造。
- 建议命名：`YYYYMMDD_HHMM_采购编号或待识别_物品简称_序号.ext`，同名不覆盖他人文件。上传实际到货/开箱/缺损证据，多物品合照只需一份文件并关联多个采购行。
- 以媒体ID/文件内容哈希优先去重，辅以上下文识别转发；相同物品的另一张有用照片可保留但不增加到货量。消息编辑/更正产生的新事实不能被旧去重标记吞掉。
- 上传后打开文件或检查列表和预览，确认正确父目录、文件名、图像可读，并记录飞书链接。保存上传成功/待重试状态，不仅凭上传按钮或本地保存称归档完成。

## 飞书写回

1. 读取目标房源真实关联字段与稳定记录ID，核实表、地址、范围及行数；从当前字段配置查清到货状态字段及合法选项。缺字段、字段含义不明或共享行无法只改本地址时，先报告，不能替用`购买进度`或更改表结构。
2. 建立已核实的逐行变化清单，保存原值、拟改值、数量依据与证据。只更改用户要求的到货状态；内部运行记录保存收货量和证据，不未经授权改其他列。
3. 若只有“到货/未到货”两种选项，确认全部有效数量到齐后才标到货；部分到货在运行记录和报告说明，保留能准确表达未全部到货的原状态。不为方便擅加选项。
4. 写前重读当前行，保留同事新写入的退货/损坏/取消等例外；已是正确值不重复写。遇到证据冲突不无声覆盖。确需纠正已有错误到货状态，须有明确更正证据并记录原因。
5. 保存后独立读回同一记录ID/字段核对。报告实际成功条数及未完成条数，失败项留待重试，不把拟改清单当已完成；既有正确值单独计为“无需更新”。

## 每个真实setup的持久记录

在任务的`work/setup-<稳定房源标识>/`保存JSON或等价结构化记录，不把这些房源数据写进技能：

- `scope`：完整地址、管理类型、房源/采购表ID、源目录和照片目录ID/链接、指定各群标识、Floorplanner方案与首日版本。
- `schedule`：启动时点、原始截止日、当地时区、每日检查时间、实际自动化ID、active/overdue/completed/ended状态。
- `cursors`：每个群最后完整读取的消息/时间与本次覆盖区间；图片读取/下载失败的单独待办。
- `handoff`：首日每份图/PDF的版本或哈希、发送状态、可用消息ID/时间。
- `receipts`：上述收货事件、累计口径、匹配行、异常、照片本地索引与飞书链接。
- `actions`：上传、发送和表格更新分别记录planned/in-progress/verified/failed/uncertain，保留修改前后值。
- `issues`：人员汇报的未完成事项、已知负责人/承诺日期、证据、是否影响工期；以及未通知过的有意义变化。

游标、动作完成状态分开推进：聊天完整读取后可保存读取位置，但下载、上传、发送、写回失败仍须保持待办，不能随游标丢失。读取不完整时保留缺口及原成功位置供补扫。恢复先读运行记录和平台实际状态，避免重复发首日资料、重复上传或累计。

发送/上传/写回结果不明时，先检查目标会话/目录/记录是否已有结果。确认没有才重试一次；仍不明则保留uncertain并报告，不盲目反复发送或覆盖。所有操作以可验证结果为准。

## 每日自动化

真实任务的时间确定后，使用当前`automation_update`工具；同房源同群已有自动化则更新并保留用户设置。调度提示词用清楚的中文包含：

> 使用 $setup-group-arrival-followup 跟进已绑定的房源与微信/WhatsApp群，读取本任务保存的范围及状态，每天补扫新消息和图片，核对同地址setup发票和新采购总表，归档到货照片并更新已核实采购行的到货状态，跟踪安装摆放与未完成事项。保持原始两周截止日，到期未完成时标明逾期并继续每日检查。首日只补尚未发送的交底资料。状态未变或没有可处理的新信息时保持安静；仅在实际进展、重要差异、工期风险、完成、失败或需要用户处理时通知，相同未变阻塞不重复通知。按既有验收规则确认完成或用户明确结束后停止本房源自动化，并如实保留遗留项。

保存提示词前代入准确房源、群、状态文件绝对路径、时区、时间及截止日，不把通用示例直接作为未知范围的任务运行。每天检查不等于实时监听；只有工具确认调度已生效才称每日跟进已安排。

每日结果优先呈现有变化的事实：新增收货及部分到货、实际写回、实际归档、布置进度、距截止日/逾期天数、需要处理的缺项。件数口径不统一时按采购行分别列明，避免给出误导的总体百分比。
